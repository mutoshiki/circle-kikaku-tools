# 企画タブ内へのフォーム・登山計画書統合

## 利用者の目的と順序

企画名・タブを残したまま、応募フォームと登山計画書の作成を行う。実装順は利用者指定のとおり、①フォームメーカーのタブ内統合 → ②登山計画書の下書き保存・復元 → ③登山計画書のタブ内統合 → ④Carbon MCPとCarbon Builderによるサイト全体のUI統一とする。本依頼は計画策定のみ。

## 採用する構成

- 同じReact画面の中でツール本体を表示する。共通ヘッダー・企画名・ツールタブは1組。ツールごとの別ヘッダーと起動専用の説明画面は省く。
- フォーム・登山それぞれの元リポジトリに再利用パッケージを置く。元サイトも同じソースを利用し、企画サイトはバージョン・元SHA・checksumを固定した配布物を取り込む。開発者の別worktreeへの相対importを使わない。
- フォームのFirebaseキュー・専用Apps Script worker・既存企画接続契約を再利用する。画面統合を理由にworkerやGoogleアカウントを変更しない。
- 登山は保存可能なデータと画面処理の境界を先に作る。既存の画像解析・行程編集・PDF生成を再利用し、全機能のReact再実装は要件にしない。
- iframeを最終構成にしない。ブラウザの二重スクロール、テーマ・フォーカスの分断を避けるため、直接組み込める公開APIを作る。既存global runtimeをそのままホストへ読み込む案も採らない。

## 下書きの初期仕様（設計側の推奨）

企画別のIndexedDB保存。入力・行程・画像・編集中の段階を自動保存し、再読み込み後に復元する。画像はバイト列とMIME型で保存して読み込み時にBlobへ戻し、旧Blob形式も読める。object URLは永続化しない。通常利用に手動保存・読込・削除メニューを置かず、保存結果は短い通知で伝える。保存障害時に、残っている入力内容を退避する書き出しだけを復旧操作として示す。クラウド同期・他端末での自動復元は追加しない。画面の状態表示は「この端末に保存しました」とし、企画データの「同期完了」と混同させない。

端末間の下書き共有が必要になった場合は、画像ストレージ・権限・競合処理を含む追加計画に切り出す。通常利用の手順を増やすファイル持ち運び操作は追加しない。

## 保護する仕様

- 既存の企画URL、参加者確定・属性同期、車割・班割・精算、Windows学務書類の経路を維持する。
- タブの固定解除・ツール取り外しで、フォーム連携・作成中job・登山下書きを削除しない。
- 企画Aの下書き・job・権限情報を企画Bへ流用しない。戻る／進む、直接URL、複数タブでも同じ。
- フォーム作成は明示操作時だけ。タブを開く、再描画する、再読み込みするだけで新jobや予約を発行しない。
- Googleフォーム本体の編集／回答用画面、PDF表示・共有は必要に応じて外部表示する。メーカーの入力・作成状況のための別サイト遷移をなくす。
- UI統一は、文字・余白・操作・文言・状態表示を整える。精算計算や参加者確定手順の再設計を便乗させない。

## UIの目標

応募フォームタブは、未作成なら入力と作成操作、処理中なら作成状況、連携済みなら応募用リンク・編集用リンクなどの結果を表示する。同一企画に別フォームを作る操作は設けない。別の端末が持つ非公開のjob情報・編集権限を取得できると約束しない。

登山タブは、既存の「基本情報 → YAMAP → 確認」の手順を本体として表示する。企画の実施日は、対応する入力欄が空で下書き復元が完了した後に初期値として内部同期する。保存済み下書きと入力済みの値は優先し、企画名を山名に流用しない。同期の説明文や確認操作は表示しない。

全体の統一対象は企画一覧・作成・参加者・車割・班割・精算・ツール管理・応募フォーム・登山計画書と、それらのモーダル、メニュー、トースト、空／読込／エラー状態。学務書類はサイト内の案内とCSV画面までとし、WindowsアプリのUI改修を含めない。

## 採用しない案

| 案 | 理由 |
|---|---|
| 別サイトをiframeに入れるだけ | 画面の分断・保存・フォーカス・PDFの問題を残す。短期のデモに使えても完成条件にしない |
| 元アプリを丸ごとコピーして別々に改修 | 不具合修正が分岐する。版管理された共通ソースにする |
| 下書き画像をroomのRTDBへ追加 | 画像容量と権限・旧client互換の変更を同時に持ち込む |
| 全画面を同じカードや同じ情報密度にする | フォーム・名簿・精算・印刷書類では目的が違う。共通ルールと画面固有の密度を両立する |

## 根拠

実装計画書の「調査済みの現在地」に確認したSHA・ファイル・既存APIを記す。Carbonの公式指針と具体的な画面設計の判断も計画書で分ける。
