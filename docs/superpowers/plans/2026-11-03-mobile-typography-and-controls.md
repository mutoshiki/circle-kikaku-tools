# モバイルの文字・操作領域・ツール内レイアウト改善計画

作成日: 2026-11-03。状態: 実装・ローカル検証済み。CIと本番公開は標準リリースフローで実施中。

## 1. 目的と対象

小さい文字を追う負担、押し間違い、過剰なスクロールを減らす。文字・ボタンを一律に拡大せず、役割と使用頻度に応じて調整する。

対象は企画一覧・作成、共通ヘッダー、全7ツールのタブ、タブ編集、各画面から開くモーダル・メニュー・折り畳み・入力エラー。既存の公開UIを土台とする。
企画のデータ構造、計算、同期、保存方法の変更は含めない。説明文・確認操作を増やして解決しない。

## 3. 採用するサイズ基準

Carbon公式の基準と、このサイトで決める基準を混同しない。
公式は役割ごとの文字スタイルと対応する行高、一貫した余白スケール、コンポーネントの構造を提供する。以下のモバイル向け具体値は本サイトの推奨案で、Carbonの一律の必須値ではない。

| 役割 | モバイルの開始案 |
| --- | --- |
| ページ見出し（一覧・作成など） | 24、行高32 |
| タブ内の主見出し/モーダル題名 | 20、行高28。人数などのコンパクトな見出しは16も可 |
| 小見出し/人物名/本文 | 16、行高22〜24 |
| 入力値/検索語 | 16以上。ブラウザの文字拡大を妨げない |
| 入力ラベル/エラー/操作に必要な説明 | 14、行高20 |
| 補足日時/件数/非操作タグ | 12〜14。重要情報を12へ落とさない |
| ボタン文字 | 主操作16、短い補助操作14を開始案とする |
| ボタンの操作領域 | 原則48、高密度な補助操作も最低44。アイコンは16〜20でよい |
| チェック/ラジオ | マークの拡大より連動するラベル行を44以上にする |
| アコーディオン/summary | 文字14〜16、開閉領域48以上。長文は折り返して高さを伸ばす |
| 通常入力の高さ | 48を開始案。複数行入力は内容とrowsで調整 |
| 左右余白/項目の間隔 | 本文16、ラベルと値4〜8、関連項目8〜16、セクション24程度 |

画面全体の文字を大きくして一覧密度を失わない。太字は見出し・重要な集金額を中心にし、車名や全金額を太字に戻さない。
長い人名・大きい金額・日本語操作名は縮小や省略で収めず、行/列構成を切り替える。
モバイル判定は既存671/672の境界を整理し、必要なら`pointer: coarse`を補助条件にする。狭い幅だけでPC表示まで大きく崩さない。

## 5. 変更場所と実装方法

1. `apps/react/src/styles/_ui-foundations.scss` に役割ごとの文字/行高/操作領域の基準を追加。余白の既存変数を再利用する。
2. `styles.scss` の既存指定を統合する。`size="sm"`がモバイルで32pxになる場所は、Carbon標準propsで必要サイズを指定できるかを確認して変更する。部品の内部DOM全体への強制font-size指定は避ける。
3. `ui/SectionHeading.jsx` と学務書類のh2を統一する。見出しの意味上のレベルと見た目を区別する。
4. モーダルの共通枠は既存を使う。モバイルの下端配置、スクロール領域、フッター64pxを保ち、`white-space: nowrap`による長文切れを解消する。全モーダルへ固定高さを強制しない。
5. 小さな小分類タブ、タグ、チェックマークは、操作可能なものと表示専用を区別。フォーカス用1px sentinelや隠しinputはボタンサイズ監査から除外する。
6. 統合パッケージはソース側で修正し、vendor更新で取り込む。`node_modules`やminify済みdistの直接編集はしない。
   - フォームのソース候補: `C:/Users/toshi/Documents/GitHub/sanpokai-kikaku-portal/src/features/form-maker/`。
   - 登山のソース候補: `C:/Users/toshi/Documents/GitHub/tozan-keikaku-syo-maker/src/styles.scss`、`src/App.jsx`。`.progress__step`は420px以下で`.6875rem`になる指定がある。
   - インストール済みpackageとソースcheckoutの一致、ビルド/梱包対象、分離worktreeを確認してから編集する。過去のcheckoutを最新版と仮定しない。
7. 印刷PDFのpt単位と画面のpx単位を分離する。画面改善でPDF組版を変えない。

## 7. 合否基準

- 320〜430pxで本文の横はみ出しなし。タブと表など意図した局所スクロールは識別可能。
- 主操作48、補助操作44以上を原則とし、例外は操作頻度・隣接間隔を理由付きで記録。隣接操作の領域が重ならない。
- inputの可視文字16以上。日本語ラベル/エラーを無理な1行にせず、対象項目との関係が分かる。
- 文字拡大200%時も操作/値/通知を読める。縮小で逃げない。iOSの自動ズームとソフトキーボードは実機または実際のSafariで別確認する。
- 長い人名・レンタカー・7桁金額・負数・区分2つ・長いメニュー/削除文・日本語入力中を対象にする。
- モーダルは先頭・中間・末尾で閉じる/戻る/主操作が使える。背景が誤スクロールしない。閉じた後は起点へフォーカスが戻る。
- accordion/summaryは複数展開/長い見出し/矢印状態/キーボードでも確認。本文の余白と開閉操作の押しやすさを両立する。
- ライト/ダークを代表画面で確認。通知は本文・操作を覆い続けない。
- 集金・計算・参加者確定・タブ保存などの処理契約は既存checkで保護。画面寸法のテストでデータ処理のassertionを弱めない。
