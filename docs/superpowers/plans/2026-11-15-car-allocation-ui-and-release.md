# 車割の見やすさと操作導線の改善計画

> **実装担当:** `superpowers:executing-plans` を使い、各工程の完了をチェックする。サイドブラウザで実際に操作し、合格した版を標準手順で公開する。

**目的** — 主催者が車割を開いて、割り当て状況・運転手・乗員をすぐ確認し、必要なときだけ配置を変更できるようにする。

**設計** — 既存の割り当ての表示データとCarbonコンポーネントを使い、状態に応じた見出し・操作の順序・乗員行を整える。共通のタブ列は、狭い画面での横送りと選択タブの見え方だけを調整する。

**仕様** — 2026-11-15の車割スクリーンショットと直前のUI改善案。画面・操作の受け入れ条件は以下に記載する。

## 変更範囲

| ファイル | 担当 |
| --- | --- |
| `apps/react/src/components/Allocation.jsx` | 状況の判定と表示、ランダム操作、車・班見出し、乗員行、フォーカス |
| `apps/react/src/styles.scss` | 車・班のまとまり、長い氏名・役割・メニューの配置、タブの表示 |
| `apps/react/src/App.jsx` | Carbonの現在の矢印動作を確認し、スタイルだけで着地がそろわない場合にタブ送りを調整 |
| `apps/react/tests/browser/allocation.spec.js` | 車割・班割の状態、確認ダイアログ、読みやすさと操作の回帰 |
| `apps/react/tests/browser/project-workspace.spec.js` | モバイルのタブ送り、選択・URL・フォーカスの回帰 |

保存・同期・割り当て計算・固定や役割の判定には既存処理を使う。`projectAllocation(room, type)`、`getCapacitySummary(type, capacity, memberCount)`、`runtime.store.command('randomize', { type })` を利用する。登録なし、席の追加、候補の一覧、車や班を削除したときの確認と手動移動を既存テストで確認する。班割は同じ画面を共有するため、班・班長の文言と班の定員ルールを使い、車割と両方確認する。

## 1. 画面上部とランダム操作

- [x] 既存の `allocation.spec.js` の概要・モバイルのテストを更新する。参加者13人・3台・未割り当て0人なら「全員割り当て済み」と「13人・3台」、未割り当て2人なら「未割り当て 2人」と「未割り当てを見る」が表示されることを確認する。割り当て済みでも定員超過があるケースでは、正常な完了表示の代わりに警告を出す。超過と未割り当てが重なる場合は、警告と未割り当て導線の両方を出す。
- [x] `Allocation.jsx` で車ごとの実人数と定員を既存の定員ヘルパーから取得し、超過を先に表示する。該当する車の見出しにも「定員超過」を表示する。未割り当ての導線は既存の一覧を展開して移動し、キーボード操作でも移動先が分かるように開閉ボタンへフォーカスを移す。参加者0人の既存案内を確認する。
- [x] 車や班を作っただけで、運転手・班長以外の乗員がまだ配置されていなければ「ランダムに割り当てる」。乗員がすでに配置されていれば、未割り当てが残っていても「ランダムに組み直す」。ボタンの判定には現在の配置を使う。確認画面では前者は割り当て、後者は既存配置も変わり得ることを伝え、両方で役割者と固定した人の扱いを明記する。全員割り当て済みでは組み直しを控えめな操作にする。
- [x] 常設の「実行 0回」とその読み上げを外す。回数の記録と実行結果の通知は現行処理を使う。ダイアログの種類は表示文言で判定せず、`kind: 'randomization'` を使ってランチャー参照とフォーカス復帰を維持する。
- [x] 「割り当て済み＋未割り当て」の混在、「キャンセル・Escで配置が変わらずフォーカスが戻る」、「確定で固定した人・運転手の配置が保たれる」を対象テストで確認する。

> 定員超過の集計は車割・班割双方の単体テストで確認した。通常の保存・移行処理は過員データを正規化するため、現行のデータ経路で不正な超過状態を保持するE2E fixtureは追加していない。画面の警告分岐は防御的に実装し、実データ経路でのE2E確認は未実施。

## 2. 車・班と乗員の見やすさ

- [x] 車ごとの見出しに薄いテーマ色を使い、車名、乗車人数／定員、車のメニューを一行で確認できるようにする。既存リストとの区切りを保ち、乗員行の上下余白を詰める。長い車名でも定員とメニューが隠れないようにする。
- [x] 氏名の近くに「運転手／班長」「固定」などのタグを並べ、学年と乗員メニューを右側にそろえる。長い氏名・複数タグ・メモは折り返せるようにし、メニューが押し出されないようにする。タップ領域を44 CSS px以上確保し、車／班のメニューは「A車の設定」など、乗員メニューは氏名＋「の操作」で区別する。メニュー内の既存操作と順番を確認する。
- [x] `allocation.spec.js` の長文・200%ズーム・メニュー確認を更新する。狭い幅でページの横スクロールが増えず、氏名・運転手タグ・定員・メニューを確認でき、押すと対象のメニューが開くことを確認する。

## 3. モバイルのタブ送り

- [x] 現行のCarbon `Tabs` / `TabList` の実DOMで、タッチ横送り・矢印・選択タブの自動表示を確認する。矢印を押して停止した後は端のタブが一文字だけ見える位置を避け、次／前のタブの境界にそろえる。矢印の表示領域も含め、選択中タブのラベル全体が見える位置に調整する。手で横送りした時は通常どおりスクロールし、選択タブの表示調整は初期表示・選択変更・幅変更で行う。
- [x] 既存Carbonのスクロール面で調整し、タブのDOMやキーボード操作はそのまま使う。ブラウザーテストでは390px前後で「車割」直リンク、左右のスクロール矢印、タブ選択、ブラウザーの戻る／進む、キーボードでの選択を確認する。スクロール矢印だけではアクティブタブやURLを変えない。

## 4. サイドブラウザで改善を繰り返す

- [x] 実装を開始する時点でGitHub `main`・公開manifest・作業差分を照合し、適切なクリーンな作業場所を選ぶ。公開SHAを基準に `npm --prefix apps/react run build:preview -- --baseline-source-sha <公開SHA>` でローカル専用ビルドを作る。空きポートでVite previewを起動し、`npm --prefix apps/react run check:preview -- --url <ローカルURL> --expected-source-sha <公開SHA>` を通す。再ビルドしたら再照合し、古いキャッシュが残る場合は新しいローカルポートを使う。
- [x] サイドブラウザのローカルプレビューで、まず全員割り当て済みの画面を開く。未割り当ては、架空の乗員をメニューから「未割り当てに戻す」で再現する。超過・長い氏名はofflineテストのfixtureで再現する。サンプルは状態を確認するために使い、サンプル自体は作り込まない。本番企画IDと本番データは使わない。
- [x] 320〜390px幅とデスクトップで、車割・班割を実際に操作する。ライト・ダーク両方で見出しと区切りを見て、①最初の画面で割り当て状況が分かる、②車名・人数・運転手の対応が見える、③未割り当てと組み直しの導線が分かる、④長い表示で横はみ出しやメニューの切れがない、⑤矢印・キーボード・Escが機能する、を合格条件にする。
- [x] 気になる点を「状態・画面幅・操作・直す箇所」で記録し、修正→再ビルド→配信元の照合→サイドブラウザで同じ操作を再確認する。差分が共有UIに及んだ場合は班割とタブ移動も確認する。最終版が上記5条件を満たすまで繰り返し、合格した車割画面をサイドブラウザに残す。サイドブラウザに接続できない場合は、ローカルの自動検証までは進め、画面確認と公開を保留する。
- [x] 自動検証はoffline設定で `npm --prefix apps/react run test:browser -- tests/browser/allocation.spec.js tests/browser/project-workspace.spec.js tests/browser/randomization-count.spec.js --project chromium-desktop --project chromium-mobile --project webkit-mobile --workers=2` を実行し、対象が実行され成功したことを確認する。3ブラウザーで87件、再実行ですべて成功。

## 5. 合格した版を本番へ反映

- [ ] 合格した差分だけをコミット・pushし、PRを作成する。共有タブやイベント処理を含む場合はCIの分類に従い、必須チェックを通してマージする。PR後に動作や表示を修正した場合は、影響するサイドブラウザの確認をやり直す。
- [ ] マージ後のmain SHAで `Release / Readiness` が成功してから既存の `React Production Release` を実行する。公開経路はワークフローの分類に従う。現行の実行ごとに生成する専用企画IDでChromium／WebKitの本番スモークとcleanupを確認する。失敗時は既存のロールバックを確認し、原因を修正して対象工程を再検証する。
- [ ] 本番rootのHTTP 200と `release-build.json` の `sourceSha`・`assetDigest` をリリース成果物と照合する。読み取り専用で確認できる画面があれば、表示も確認する。PR、公開SHA、サイドブラウザの確認結果、本番スモークとcleanupの結果を報告して終了する。
